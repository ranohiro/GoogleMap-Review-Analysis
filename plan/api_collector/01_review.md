# 原案レビューと改善提案

- 対象: [00_original.md](00_original.md)（サードパーティAPIを活用したGoogleマップレビュー収集アプリ 構築計画書）
- レビュー日: 2026-10-31
- 追記（同日）: Outscraper の無料枠は Web 画面からの CSV/XLSX ダウンロードのみで API は有料、とわかったため、無料枠で Outscraper と Apify を比較する計画に改訂（[02_design.md](02_design.md) v1.1）
- 方法: 原案を既存コード（`src/scraper.py`, `src/parser.py`, `src/pipeline/*.py`）と既存データ（`data/raw/`, `data/annotations/`）に照らして確認

## 結論

方針（既存コードを触らない／`data/raw/` 経由で既存パイプラインにつなぐ／Outscraper 優先）は妥当です。
ただし原案どおりに作ると、**エラーにならないまま分析結果が壊れる箇所**が 7 つあります（下表の 🔴）。どれも設計で回避できるので、改訂版の設計 [02_design.md](02_design.md) に反映しました。

| 区分 | 件数 | 意味 |
|---|---|---|
| 🔴 必須修正 | 7 | 直さないとデータの欠落・重複・不整合が起きる |
| 🟡 改善推奨 | 9 | 課金事故・手戻り・保守コストを減らす |
| 🟢 補足 | 6 | 将来の分析や判断に役立つ情報 |

## 🔴 必須修正

### R1. カラム定義が既存の新形式と合っていない（原案 §4.2）
- `normalize.py:90` は **`relative_time` 列があるかどうか**で新形式／旧形式を判定します。新形式の属性列名は `reviewer_attributes` です（`normalize.py:95`）。
- 原案は `relative_time` と旧形式の `attributes` を同時に出力するため、属性列が読まれません。
- 原案には `store_name`, `reviewer_id`, `is_local_guide`, `reviewer_review_count`, `updated_time` もありません。
- **対応**: raw CSV の列は `scraper.py:37` の `OUTPUT_COLUMNS` に `source_url` を加えたものにそろえる（[02_design.md §3](02_design.md#3-データ契約raw-csv)）。

### R2. 日時のタイムゾーンがずれる（原案 §4.2 `review_datetime_utc`）
- 既存パーサーは日時を **JST に変換し、タイムゾーン情報を外した値**で保存しています（`parser.py:58`）。
- UTC のまま書くと 9 時間ずれ、日付をまたぐ口コミは投稿日が変わります。
- **対応**: API の UNIX 時刻（または UTC 文字列）を JST に変換し、`YYYY-MM-DD HH:MM:SS` で書く。

### R3. 「店舗ごとに最新ファイルだけを使う」ルールと件数上限・差分取得がぶつかる（原案 §6-2, §6-3）
- `normalize.py:127-128` は、既定では **店舗ごとに最新の raw CSV 1 ファイルだけ**を使います。
- 件数上限（例: 500 件）付きで取得すると、それが最新ファイルになり、以前に全件取得した分が**黙って分析から消えます**。差分取得（新着のみ）でも同じです。
- **対応**: 分析対象店舗は「全件スナップショット」を基本とする。上限が総件数より少ないときは CLI が警告する。差分取得は `normalize --all-snapshots` と組み合わせる運用を確立してから導入する（バックログ）。

### R4. 口コミIDが変わり、人手の正解ラベルと LLM キャッシュがつながらなくなる
- 現在の raw CSV（2 店舗分）は旧形式で `review_id` がないため、`review_uid` は `h_` + ハッシュ値です（`normalize.py:54-58`）。
- `data/annotations/gold_sample.csv`（人手ラベル）と LLM キャッシュのファイル名（`tag_aspects.py:70-74`）は、この `h_` 形式の ID に依存しています。
- API データには `review_id` があるので、取り込むと `review_uid` が変わり、**人手ラベルとの突き合わせ件数が 0 件**になり、LLM タグ付けもキャッシュが使えず再課金になります。
- **対応**: ID 移行ツール `src/api/migrate_uid.py` を新規に作る（既存コードは変更しない）。手順は [02_design.md §10](02_design.md#10-既存データの移行review_uid)。

### R5. 同じ店舗で Playwright 版と API 版の CSV が混ざると重複する
- ID の体系が違う（`h_` ハッシュ と API の `review_id`）ため、`--all-snapshots` で統合すると同じ口コミが 2 回数えられます。
- **対応**: 1 店舗につきデータの取得元は 1 つにする。API に切り替えた店舗の旧 CSV は `data/raw/_archive/` に移す（`normalize` はサブフォルダを読まない）。

### R6. `data/raw_json/` が Git の除外対象になっていない（原案 §3, §4 TIP）
- 生 JSON には投稿者名などの個人情報が含まれます。現在の `.gitignore` は `data/raw/` と `data/debug/` しか除外していません。
- **対応**: 保存先を `data/raw_vendor/`（API の応答とダウンロードしたファイルの両方を置く）に改め、`.gitignore` に追記する（Phase 0）。

### R7. 店舗を「何番目か」で指定していて、マスタと対応しない（原案 §4.1 `store_idx`, §5 `--store 1`）
- `normalize` は **ファイル名の `store_N`** と **`source_url` が `stores.csv` の `url` と完全に一致するか**で店舗を特定します（`normalize.py:76-85`）。
- ファイル名は正規表現 `reviews_(store_\d+)_(\d{8}_\d{6})\.csv$` に一致しないと**黙って無視**されます。`_api` などの接尾辞は付けられません。
- 原案の `source_url = place_id` は `stores.csv` の `url` と一致しません。
- **対応**: 店舗は `stores.csv` の `store_key`（`store_2` など）で指定する。`source_url` には `stores.csv` の `url` をそのまま書く。どちらのツールで取得したかは manifest（実行記録）で管理する。

## 🟡 改善推奨

### I1. フェーズの順番を「変換処理を先に、課金は最小に」へ
原案は「クライアント → フォーマッタ」の順ですが、PoC で 1 回だけ実データを取り、その JSON を使って**課金なしで変換処理とテストを先に完成**させる方が、試行錯誤による課金と手戻りが減ります。

### I2. 変換処理（フォーマッタ）はプロバイダごとに持つ
API のフィールド名はサービスごとに違うので、共通の `formatter.py` 1 つでは吸収できません。
「プロバイダ: 生 JSON → 契約どおりの行（dict）」「共通 writer: 行 → CSV・JSON 保存・実行記録」に分けます。

### I3. 非同期タスクの二重課金を防ぐ
Outscraper の非同期方式では、タイムアウト後に再送すると**同じ取得が 2 回課金**されるおそれがあります。
- 送信（submit）は自動リトライしない。受け取ったリクエスト ID をすぐ manifest に記録する。
- 中断したときは `--resume <request_id>` で、課金なしで結果だけを回収する。

### I4. コストガードを具体的にする
「確認プロンプト」だけでは基準があいまいです。以下を設計に入れました（[02_design.md §7](02_design.md#7-コストガード)）。
- `--dry-run`（API を呼ばずに見積もりだけ表示）
- 金額のしきい値を超えたら確認する（`--yes` で省略可、対話できない環境では中止）
- 1 回の実行で取得できる件数に上限を設け、超える場合は設定ファイルを直さない限り実行しない
- 取得件数が総件数より少ないときの警告（R3）

### I5. ファイルから CSV を作れるようにする（`--from-file`）
ダウンロードしたファイル（Outscraper の無料枠）の取り込みと、変換処理を直したあとの作り直しを、同じ仕組みで課金なしに行えます。

### I6. テストを用意する（ネットワーク不要）
現在のリポジトリにはテストがありません。匿名化した小さな JSON を使って、変換処理と `normalize.build()` の結合を自動で確認します。

### I7. 追加ライブラリは不要
`requests`, `python-dotenv`, `tenacity` はすでに `requirements.txt` にあります（原案 §3 の「requests 等を追記」は不要）。Outscraper の公式 SDK は使わず、HTTP を直接呼びます（非同期処理とリトライを自分で制御するため）。開発用に `pytest` だけ追加します。

### I8. 短縮 URL を Place ID に変換しておく
`stores.csv` の URL は `maps.app.goo.gl/...` の短縮 URL です。API が受け付けるかは PoC で確認し、受け付けない場合に備えて `stores.csv` に `place_id` 列を追加します。`normalize` は列名を指定して読むので、列を足しても影響はありません。
`store_1`（店名要確認）の店名も API の結果で確定できます。

### I9. 「1 行も変更しない」範囲をはっきりさせる
原案のままだと `.gitignore`・`README.md`・`stores.csv` の更新まで禁止に読めます。
「**既存コード**（`src/` 直下の 5 ファイルと `src/pipeline/`）は変更しない。設定・ドキュメント・マスタは追記のみ可」と定義しました。既存関数の import による再利用は可とします。

## 🟢 補足

### N1. 料金・無料枠・フィールド名の確認
- Outscraper: 無料枠は**月 500 件・CSV/XLSX ダウンロードのみ**で、API は有料の Medium 以上（501〜100,000 件で $3/1,000 件）。原案の「初月無料枠」「$2〜3」は不正確でした。
- Apify: 毎月 $5 分の無料クレジットがあり、公式 Actor の単価は $0.35〜0.50/1,000 件程度の表示。ただし無料プランでは件数の制限があるという情報もあり、未確認です。
- 原案のフィールド名（`reviewer_characteristics`, `response_from_owner_text` など）は Outscraper の名前ではなく、Apify の名前に近いものが混ざっています。
- いずれも Phase 0〜1 で公式ページと実データから確定します。

### N2. 項目別の評価（料理・サービス・雰囲気など）を分析の検証に使える
Outscraper の応答には、Google マップで投稿者が任意で付ける項目別評価が含まれる可能性があります。含まれていれば、LLM による観点タグ付けの精度を外部データで確かめる材料になります（[analysis_proposal.md](../analysis_proposal.md) の検証方針を補強）。PoC で有無を確認します。

### N3. 原文か翻訳文かを確認する
[analysis_proposal.md §5-2](../analysis_proposal.md) で懸念されていた「Google が翻訳文を返していないか」は、API でも同じ確認が必要です。インバウンド分析（§3-3）に影響するため、PoC のチェック項目に入れました。

### N4. 自店舗なら Google Business Profile API という選択肢もある
分析対象の店舗の Google ビジネスプロフィールを管理する権限がある場合は、公式の Business Profile API で自店舗の口コミを全件取得できます。権限がなければ対象外です。

### N5. プロバイダの抽象化は最小限にする
2 社目を実装する予定が決まるまでは、インターフェース定義と Outscraper の実装 1 つだけにします。

### N6. ログファイル名
`src/logger.py` を再利用するとログファイル名は `scrape_*.log` になります（変更不可のため）。ログの 1 行目に `[api]` と書いて区別します。
